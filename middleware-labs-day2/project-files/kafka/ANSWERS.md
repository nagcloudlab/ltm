The producer hashes the key, so every `acc-1001` event goes to the same partition (partition 1 with 3 partitions); a partition is an append-only log read in offset order by exactly one member of a group, so the events are processed in the order sent. The cost: a very busy key makes one **hot partition** — all its lag sits on one partition and one consumer, and adding members does not help it.

It is **idle** (`#PARTITIONS 0` in `--describe --members`): a partition is read by at most one member of a group, so with 3 partitions only 3 members work; the fourth is a standby that takes over in the next rebalance if a member leaves. To use four, the topic needs at least 4 partitions (`kafka-topics.sh --alter --partitions …`) — note this changes which partition each key maps to for new events.

7. Changing offsets under running members would race with their own commits and the next commit would overwrite the reset. The group must be inactive (state `Empty`). Stop every member (Ctrl+C / stop the service), confirm with `--describe --state` (`#MEMBERS 0`), run the reset with `--dry-run`, then `--execute`, then start the members again.
8. A `--to-datetime` value without a zone is read as **UTC**, so `10:00` meant 15:30 IST — later than the newest event, so every partition was "empty" and the tool fell back to the latest offset. Use the zone (and the milliseconds): `--to-datetime 2026-11-15T10:00:00.000+05:30`, or the UTC time `2026-11-15T04:30:00.000`. Always check the plan with `--dry-run` first.
