# Day 2 — Check yourself answers

## Lab 1 — RabbitMQ: Check yourself answers

1. **SMS gateway down for 10 minutes.** With a broker, the payment service publishes PaymentCompleted and finishes; the events wait in queue `sms` (`messages_ready` grows) and the SMS go out when the consumer recovers. Without a broker, the payment service calls SMS directly, so each payment waits for a timeout or fails because of SMS, and the SMS for that period may be lost.

2. **"published" but no new message.** (a) The routing key matches no binding (typo such as `paymnet.completed`) — the exchange drops it silently; `rabbitmqadmin publish …` with the same key prints `Message published but NOT routed`, and `sudo rabbitmqctl -q list_bindings source_name destination_name routing_key` shows the keys that do match. (b) A consumer is attached and took it at once — `sudo rabbitmqctl -q list_queues name messages_ready messages_unacknowledged consumers` shows `consumers` above 0 and the consumer's output shows the message. (A wrong exchange name is not silent: `404 NOT_FOUND - no exchange`.)

3. **Ready 0, unacked 10, consumers 1, unchanged.** The consumer took its full prefetch (10) and never acks — it hangs or forgot `basic_ack` (like `sms-noack.py`). Nothing else gets those 10 while it stays connected. When it disconnects (Ctrl+C, crash, or the broker's 30-minute `consumer_timeout`), the 10 return to `messages_ready` and are delivered again with `redelivered=True`.

4. **Topic routing.** `fraud` is bound with `payment.#` (`#` = zero or more words), so any key starting with `payment.` matches; `sms` is bound with the exact key `payment.completed`. `payment.card.failed` also goes to `fraud` only. (`*` would match exactly one word: `payment.*` matches `payment.failed` but not `payment.card.failed`.)

5. **Two consumers.** Order is kept inside the queue, but two consumers work in parallel, so P2's SMS can be sent before P1's — no global order. Use one consumer when strict order matters. A small prefetch (e.g. 1) is better when messages take long or consumers have different speeds: a busy consumer gets no new work, so the fast one takes most (tested 19 vs 1). A large prefetch suits many quick messages, but a slow consumer can hoard work (tested 10 vs 10 while the fast one idled).

6. **requeue=True vs requeue=False.** `requeue=True` puts the message back at the head of `sms` immediately; a message that can never succeed loops for ever (tested: about 13,000 redeliveries per second) and burns CPU while blocking the messages behind it. `requeue=False` with policy `sms-dlx` sends it once to `payments.dlx` → `sms.dlq` with an `x-death` header (queue, routing key, reason `rejected`, count); `sms` keeps flowing and a human can inspect the message.

7. **sms.dlq jumped to 5,000.** Detect: `list_queues` shows `sms.dlq` growing while `sms` has a consumer. Diagnose: read a dead letter's `x-death` (`rabbitmqadmin -f pretty_json get queue=sms.dlq ackmode=ack_requeue_true`) — reason `rejected` from queue `sms` points at the consumer; match the time with the release. Recover: stop the bad release and roll back to the good consumer; only then move the messages back (`python3 dlq-move.py`, or a shovel with `src-delete-after: queue-length`). Verify: `sms` drains, `sms.dlq` returns to 0 except real poison messages, which you save as evidence before purging. Moving earlier would only fill the DLQ again.

8. **Missing after restart.** Only persistent messages (`delivery_mode=2`) in durable queues survive. `publish.py` sets `delivery_mode=2`; `rabbitmqadmin publish` sends non-persistent messages unless you add `properties='{"delivery_mode":2}'`, so those were held in memory only and lost. A non-durable queue (`sms.temp`) disappears completely with all its messages.

## Lab 2 — Kafka: Check yourself answers

1. **The event stays.** Reading only moves `notification-service`'s offset (its bookmark in `__consumer_offsets`); other groups such as `fraud-check` and later replays can still read it. Kafka deletes whole segment files by **retention** — here `retention.ms=604800000` (7 days, from `log.retention.hours=168`) and `retention.bytes=-1` (no size limit) — checked every 5 minutes (`log.retention.check.interval.ms=300000`). The active segment is never deleted.
2. **Not necessarily.** Apache's `.sha512` file is in the `gpg --print-md` layout (upper case, groups of 8, several lines), which `sha512sum -c` cannot parse. Use the supplied `kafka_2.13-4.4.0.tgz.sha512` (same hash, `hash  filename` on one line) and run `sha512sum -c kafka_2.13-4.4.0.tgz.sha512` → `kafka_2.13-4.4.0.tgz: OK`. Only `FAILED` means a bad download.
3. `active` only means the Java process started. Check that the broker finished starting: `grep 'Kafka Server started' /opt/kafka/logs/server.log` (line `INFO [KafkaRaftServer nodeId=1] Kafka Server started`), the listeners with `sudo ss -lntp | grep -E ':909[23] '`, and `kafka-metadata-quorum.sh --bootstrap-server localhost:9092 describe --status` (`LeaderId: 1`). If the line never comes, read `journalctl -u kafka` and the end of `server.log` (not formatted, wrong `JAVA_HOME`, port in use).
4. The producer hashes the key, so every `acc-1001` event goes to the same partition (partition 1 with 3 partitions); a partition is an append-only log read in offset order by exactly one member of a group, so the events are processed in the order sent. The cost: a very busy key makes one **hot partition** — all its lag sits on one partition and one consumer, and adding members does not help it.
5. It is **idle** (`#PARTITIONS 0` in `--describe --members`): a partition is read by at most one member of a group, so with 3 partitions only 3 members work; the fourth is a standby that takes over in the next rebalance if a member leaves. To use four, the topic needs at least 4 partitions (`kafka-topics.sh --alter --partitions …`) — note this changes which partition each key maps to for new events.
6. No `CONSUMER-ID` = no member is running (`has no active members`), so lag is growing because the SMS service is **down**, not slow; and the 2000 on one partition shows a hot key. First fix: start the consumer(s) of `notification-service` again and watch `LAG` drain to 0. Then look at the hot key if one partition stays behind.
7. Changing offsets under running members would race with their own commits and the next commit would overwrite the reset. The group must be inactive (state `Empty`). Stop every member (Ctrl+C / stop the service), confirm with `--describe --state` (`#MEMBERS 0`), run the reset with `--dry-run`, then `--execute`, then start the members again.
8. A `--to-datetime` value without a zone is read as **UTC**, so `10:00` meant 15:30 IST — later than the newest event, so every partition was "empty" and the tool fell back to the latest offset. Use the zone (and the milliseconds): `--to-datetime 2026-11-15T10:00:00.000+05:30`, or the UTC time `2026-11-15T04:30:00.000`. Always check the plan with `--dry-run` first.

## Lab 3 — Security: Check yourself answers

1. **401 vs 403.** Apache's 401 is an authentication failure: it does not know who you are yet, and `WWW-Authenticate: Basic` asks for credentials. Kong's 403 for `blocked-partner` is an authorization failure: the API key was valid (Kong knows the caller), but the ACL plugin does not allow that consumer's group on this service.

2. **Basic auth header.** `Authorization: Basic ...` is only base64 of `user:password`; `base64 -d` turns it back into plain text. Base64 is encoding, not encryption. Only TLS (HTTPS) protects it on the wire; it can still leak through logs or debugging output, so treat it as a password.

3. **Tampered JWT.** Kong answers `401` with `{"message":"Invalid signature"}` (PyJWT: `InvalidSignatureError`). The signature covers `header.payload`; changing one byte breaks it. With RS256 a new valid signature needs the issuer's private key, which only the issuer has — gateways and apps hold only the public key, which can check but not sign.

4. **Claims.** `iss` = who issued the token; `aud` = which API it is meant for; `exp` = expiry time; `nbf` = not valid before this time. Kong (stage 5) used `iss` to find the consumer and its key, checked the signature and `exp`. It let through a wrong `aud`, a future `nbf`, and a token sent in the URL (`?jwt=`), which also ended up in the access log.

5. **Public key, not private.** The private key can create tokens; anyone holding it can impersonate the issuer, so only the issuer keeps it. Verifiers need only the public key. With one shared HS256 secret, every service that can check tokens can also forge them, and a leak from any one service compromises all of them; rotating the secret means changing every service at once.

6. **`ImmatureSignatureError` on one server.** That server's clock is behind the issuer's (or the issuer's is ahead), so `iat`/`nbf` look like they are in the future. Quick fix: a small leeway (30–60 s) in the validator. Real fix: time sync (NTP) on every server — check with `timedatectl` (`System clock synchronized: yes`, `NTP service: active`). Never use a large leeway: it keeps expired tokens alive.

7. **Missing intermediate vs untrusted root.** Run `openssl s_client -connect host:443 -servername host -showcerts`. Missing intermediate: the chain lists only certificate `0` and the result is `Verify return code: 21 (unable to verify the first certificate)` even with the right root — the **server** team must send `fullchain` (server + intermediate). Untrusted root: the chain has two certificates (server + intermediate) and `Verify return code: 20` — the **client** team must add the root CA to the client's trust store (or pass it with `--cacert`).

8. **curl works, Java fails with PKIX.** `--cacert` only affects that curl command; Java uses its own trust store (`cacerts`) which does not contain the lab root, so it cannot build a path to a trusted root. Fixes: import the root into a truststore with `keytool -importcert` and start Java with `-Djavax.net.ssl.trustStore=... -Djavax.net.ssl.trustStorePassword=...`; or add the root to the system store (`/usr/local/share/ca-certificates/` + `update-ca-certificates`), which on Ubuntu also updates Java's `cacerts` through `ca-certificates-java`.
